# ADR 0014 — v4.5 intent-capture slim-down

- **Status**: Accepted
- **Date**: 2026-05-05
- **Supersedes**: portions of ADR-0011 (intent persistence), CLAUDE.md "Intent capture (every operator turn)" v4.4
- **Related intent**: [`docs/intents/2026-05-05-IC-012-intent-capture-v45-slim.md`](../intents/2026-05-05-IC-012-intent-capture-v45-slim.md)
- **Related plan**: [`docs/plans/active/2026-05-05-intent-capture-v45-slim.md`](../plans/active/2026-05-05-intent-capture-v45-slim.md)

## Context

The v4.4 intent + routing gate landed in IC-006 with three runtime hooks (`clear-intent-marker.sh`, `pre-edit-intent-gate.sh`, `pre-task-routing-gate.sh`), auto-injection on every operator turn, and dual-write of marker + `docs/intents/<id>.md` on confirmation. It closed the discretion gaps the agent could exploit (skipping intent capture, presenting routing silently). It worked: every confirmed intent is recorded; every Edit/Write/Bash/Task is gated.

But operating it produced four token/time costs that compound across a session:

1. **Verbose per-turn reminder** — `clear-intent-marker.sh` injects ~600 tokens of system-reminder on every UserPromptSubmit. The reminder duplicates content the agent has already loaded via `~/.claude/CLAUDE.md` and `rules/core/intent-capture-required.md`. Per-turn cost compounds: a 50-turn session burns ~30k tokens on the reminder alone.
2. **Double confirmation** — every action requires intent confirmation, then a second routing confirmation (Rule 7 of v4.4). Two operator round-trips before any tool call. The two are conceptually separable (intent = WHAT, routing = WHO) but the operator sees them as one decision and is annoyed by the two-step ceremony.
3. **Full tunnel for trivial fixes** — a typo correction goes through grill → JSON capture → present → confirm → routing declare → confirm → execute. Same ceremony as a multi-module refactor. The grill on a single-line typo is pure friction.
4. **Commit-per-discovery-artifact** — every confirmed intent commits `docs/intents/<id>.md` separately (Rule 8 of v4.4 dual-write). Plans, session journals, status updates each produce their own commit. A 1-hour slice ships 6–10 commits, half of which are discovery, not code. The git log becomes documentation churn.

Concurrent constraint: opencode interop. The plugin imports `rules/core/intent-capture-required.md` via `opencode.json` and the skill files are symlinked under `.opencode/skills/`. The operator validated opencode end-to-end in IC-009/IC-010. Any v4.5 design has to keep the protocol shape readable as a self-contained spec without assuming hook enforcement.

## Decision

Distill the v4.4 stack into v4.5 via four bundled levers. The protocol contract stays the same (intent must be confirmed before action); the ceremony around it slims.

### Lever 1 — Slim the auto-injected reminder

`hooks/clear-intent-marker.sh` lines 83–93 — the heredoc shrinks from ~600 tokens to ~95 tokens. New body keeps the three-case decision tree (action / continuation / read-only) and points to `rules/core/intent-capture-required.md` for full protocol detail. The full grill / capture / present / confirm flow is still there, but loaded once per session via `CLAUDE.md` instead of re-injected per turn.

Saving: ~505 tokens per operator turn.

### Lever 2 — Single combined intent+routing marker

A new marker name `.intent-and-routing-confirmed-<ISO>` replaces the v4.4 pair (`.intent-confirmed-*`, `.routing-confirmed-*`). The agent presents intent JSON AND routing declaration in one block; the operator's single "dale" approves both. Both gates (`pre-edit-intent-gate.sh` for Edit/Write/Bash, `pre-task-routing-gate.sh` for Task) accept the combined marker. Legacy markers are honored for one release cycle (v4.5) and removed in v4.6 to give in-flight slices a graceful upgrade.

Result: one operator round-trip per confirmation instead of two.

### Lever 3 — Trivial tier with mechanical threshold

`intent-capture` skill Step 1b assigns a tier. Trivial tier triggers IFF ALL FIVE conditions hold:

- ≤3 files touched
- ≤20 LOC changed total
- No new control flow (no new `if`/`for`/`while`/`try`/`async`)
- No new external dependency
- Category in: `typo`, `copy`, `css`, `rename`, `comment`, `string-literal`, `version-bump`

Trivial tier:
- Skips Step 2 (grill)
- Step 4 presents a one-line summary
- Step 5 writes the marker but NOT a `docs/intents/<id>.md` file
- Routing is forced to main-direct (no subagent)

The threshold is mechanical and declared by the agent in the captured JSON. Mis-classification is caught by Red Flag in `SKILL.md`. The tier is assigned BEFORE any code is touched, based on the operator's ask — not after seeing the actual diff.

### Lever 4 — Bundle discovery commits at slice close

`docs/intents/<id>.md`, `docs/plans/active/<file>.md`, `docs/sessions/<file>.md` are written to their canonical paths immediately on confirmation, plan-mode exit, and session start respectively. They are NOT committed individually. The slice's last commit (typically the same one shipping the final code change, or a final `docs: close slice <id>` commit if the slice ended without code) bundles all of them.

Survival to compaction is preserved by filesystem presence: `session-start.sh` runs `git status --porcelain` and surfaces uncommitted `docs/` files to the next session's bootstrap context. Survival to session death is preserved by the same mechanism — files are on disk until garbage-collected or explicitly cleaned.

The user-level rule "Commit after every meaningful change" still applies to code. Documentation-only churn during discovery is not a meaningful change in itself; it becomes meaningful when bundled with the code that motivated it.

Result: a 1-hour slice produces 1–3 commits instead of 6–10. The git log surfaces shipped work, not discovery process.

## Consequences

### Positive

- **~505 tokens saved per operator turn** (Lever 1) — at 50 turns/session, ~25k tokens saved.
- **Halved confirmation round-trips on standard work** (Lever 2) — one "dale" instead of two.
- **One-line confirmations on trivial work** (Lever 3) — typo/CSS/version-bump fixes ship without grill.
- **60–70% reduction in slice-level commits** (Lever 4) — git log reflects shipped work, not discovery noise.
- **Zero regression in v4.4 enforcement guarantees** — every Edit/Write/Bash/Task on the main agent is still gated by a marker; intent is still captured; routing is still declared explicitly.
- **Opencode interop preserved** — the rule file remains a self-contained spec; opencode self-enforces the protocol shape without writing marker files.

### Negative

- **Tier mis-classification risk (Lever 3)** — if the agent declares trivial when the change is actually standard, the grill is skipped. Mitigated by mechanical threshold (file count, LOC, control flow, dependency, category — all verifiable), Red Flag in `SKILL.md`, and the agent declaring tier with cited justification in the captured JSON.
- **Survival-to-compaction now relies on filesystem, not git** (Lever 4) — a `git clean -fd` or filesystem corruption between confirmation and slice-close could lose an in-flight intent. Mitigated by `session-start.sh` surfacing uncommitted `docs/` files; a manual `git add --intent-to-add` is unnecessary because the file already exists on disk.
- **Deprecation window adds hook complexity** (Lever 2) — both hooks must accept combined AND legacy markers for v4.5. Cleanup planned for v4.6 (single marker name, simpler glob).
- **Trivial tier reduces audit trail granularity** — typo fixes don't get their own `docs/intents/` file. Mitigated by recording in session journal at slice close as one-line entries; the audit trail is preserved at session granularity instead of per-fix granularity.

## Rejected alternatives

### A. Ephemeral discovery in `.claude/` with PreCompact hook auto-promote

Considered: write `docs/intents/`, plans, sessions to `.claude/intents/`, `.claude/plans/`, `.claude/sessions/` (gitignored) during the slice; a new PreCompact hook detects in-flight files and promotes+commits them before context compaction.

Rejected: complexity. PreCompact hook is a new failure surface — silent failure loses the intent irrecoverably. Survival to session death is also weaker (file disappears with the gitignored directory if the operator runs `git clean -fd` not knowing the convention). Lever 4 keeps the file at its real path on disk, where `git status` exposes it for the next session.

### B. Intents commit individually, plans/sessions bundle

Considered: keep `docs(intents): IC-N ...` as standalone commits since they are conceptually equivalent to ADRs and deserve log visibility. Only bundle plans and session journals.

Rejected: the ratio. Most slices produce 1 intent and 1 plan and several session journal updates. Standalone-intent commits leave the docs-only churn at its current level for the most common slice shape. Lever 4 trades log granularity for log signal-to-noise; the intent file is still preserved in git history, just bundled with the code that delivered the intent.

### C. Ephemeral marker only (no docs/intents file at all)

Considered: drop the `docs/intents/<id>.md` file entirely; the marker file alone is the audit token. The operator can reconstruct intent from `git log`.

Rejected: fails the "first-class development artifact" property of intents (Rule 9 of v4.5). Intents are equivalent in weight to ADRs; they describe the WHY of changes that ship. `git log` is too thin a substrate for non-trivial slices. Standard tier keeps the file; trivial tier drops it because the file would say "fixed typo on README.md:42" — the commit message already says that.

### D. Two markers, one approval

Considered: keep `.intent-confirmed-*` and `.routing-confirmed-*` as two distinct markers, but write both atomically on a single "dale". Hooks unchanged.

Rejected: the cognitive overhead. Two markers in `.claude/` for what is conceptually one decision is confusing for operators inspecting state. The combined marker (Lever 2) is simpler; the deprecation window covers backwards compatibility for one release.

## Migration notes

- Existing in-flight slices on v4.4 markers continue to work — both gates accept legacy markers for one release cycle.
- v4.6 will remove legacy marker recognition; any operator with a v4.4 in-flight slice older than the v4.6 release date must complete or restart it.
- No data migration is required for `docs/intents/<id>.md` files — the format is unchanged; only the commit policy changes.
- The `.intent-and-routing-confirmed-*` glob is added to `clear-intent-marker.sh` cleanup loop, so existing `.gitignore` patterns (`*.intent-confirmed-*`, etc.) need to be extended to cover the new marker name. Done in this commit.
