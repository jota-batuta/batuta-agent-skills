# ADR-0015: Two-phase intent marker protocol (v4.6)

**Date**: 2026-05-06
**Status**: Accepted
**Supersedes**: ADR-0014 (partial — Step 5 marker write mechanism only)

## Context

ADR-0014 established the v4.5 single-confirmation, single-combined-marker protocol. An audit identified a structural gap: the model writes its own confirmation markers (`.intent-and-routing-confirmed-*`) via the `Write` tool to `.claude/**` (exempt path in `pre-edit-intent-gate.sh`). The gate verifies that *some* marker exists but cannot verify it was written as a result of genuine operator confirmation rather than being written preemptively to bypass the grill.

**The exploit path**: On receiving an action request, a model could skip grilling entirely by (1) writing a fake `.intent-and-routing-confirmed-<ISO>` marker, (2) executing Bash/Edit in the same turn. Both steps are currently allowed: Write to `.claude/**` is exempt, and the gate only checks marker existence.

The `UserPromptSubmit` hook event exposes a `prompt` field in stdin JSON (confirmed: Claude Code 2.x hooks schema). This enables the hook to detect genuine operator confirmation phrases and write the confirmed marker externally.

## Decision

Two-phase marker protocol:

1. **Phase A (model)**: After grilling and presenting intent JSON, the model writes `.claude/.intent-pending-<ISO>` (containing the SHA-256 hash of the intent JSON). Replaces the direct confirmed-marker write in SKILL.md Step 5.

2. **Phase B (hook)**: `clear-intent-marker.sh` on `UserPromptSubmit` parses `prompt` from stdin. If prompt exactly matches a confirmation phrase AND `.intent-pending-*` exists → hook writes `.intent-and-routing-confirmed-<ISO>` and deletes pending. Otherwise → clear all markers (pending + confirmed + legacy).

3. **Guard**: `delegation-guard.sh` adds `.claude/.intent-and-routing-confirmed-*` to its kill-switch blocklist. Model Write tool calls to that path are blocked.

Confirmed markers are exclusively written by the hook (bash script outside model tool execution). Hooks are not intercepted by PreToolUse gates.

**Confirmation phrase regex** (exact match, case-insensitive, optional trailing punctuation):
```
^(dale|procedé|procede|proceda|go ahead|proceed|yes|okey|ok|confirmo|confirmed|ejecuta|hacelo|hazlo|go|sí|si|approved|listo|aprobado|continue)[.!,]?$
```

## Rejected alternatives

**A. Behavioral enforcement only** — Accept the structural gap; rely on model instruction-following. Rejected: gap is exploitable in a single turn with no operator visibility; fix is low-cost given `prompt` is available in `UserPromptSubmit`.

**B. Loose confirmation detection** (≤ N words containing keyword) — Would match "dale un vistazo" and other false positives. Exact-match is conservative and covers all documented confirmation phrases.

**C. AskUserQuestion as confirmation gate** — Structured confirmation but breaks opencode/Codex compatibility. Rejected to maintain protocol portability.

## Consequences

**Positive**:
- Confirmed markers are structurally external to the model; no instruction-following required for enforcement.
- `delegation-guard.sh` block gives a clear error if a model tries the old write path.
- Minimal UX change: operators who already send a distinct "dale" turn are unaffected.

**Negative**:
- One extra turn required: model presents intent + writes pending → operator sends "dale" → hook promotes → model executes. Previously model could execute in the same "dale" turn.
- Confirmation detection is a heuristic: unusual phrases ("dale pues", "pa'lante") don't trigger promotion.
- Opencode and non-hook tools cannot use Phase B (no UserPromptSubmit hook equivalent). They continue behavioral enforcement per SKILL.md Step 5.
